# Native desktop development

- Keep `main` as the only named branch. Do not create or retain task/topic branches. Work in the main checkout; if isolation is needed, use a detached worktree without creating a branch and preserve other worktrees' uncommitted files. Publish verified native changes directly to `main`; the legacy HTML/Electron application has been retired.
- Run automated tests on remote CI by default, including all tests that display application windows. Keep local work to static validation, building, and file/package verification. Run local tests only when the user explicitly requests them; do not fall back to local GUI execution when remote CI is unavailable.
- Obtain explicit user approval before starting an exceptionally long task or extending a bounded task into prolonged investigation or unattended follow-up. Explain the scope, expected duration/uncertainty and completion/stopping conditions first. Generic requests to improve, check comprehensively or continue are not blanket approval for open-ended work. Preserve progress and ask before an extended phase; do not invent a user-approved duration threshold, silently reduce acceptance requirements, or cancel existing work without authorization.
- When a writable non-system drive is available, new software installations, dependencies, downloads, builds, caches, temporary/generated files, fixtures, backups and packages must not be placed on the system drive. Prefer D: and detect the actual system volume rather than hard-coding C: or requiring E:. If the system drive is the only usable drive, use the existing workspace/build/package locations automatically without warning, pausing or asking for confirmation. This write/install policy does not prohibit reading existing input files or authorize moving/deleting user data; retain only genuinely OS-required system components or compatibility registration on the system volume.
- Keep 3DGS, 2DGS, and every other supported model-generation pipeline in step: plan shared workflow upgrades together, implement backend-appropriate equivalents, and test the capability matrix in the same change. Do not silently ship a 3DGS-only workflow improvement; explicitly record any unavailable capability, technical reason, and remaining acceptance gate. Never represent PLY warm starts or previews as full optimizer-state resume.
- Every new or changed user-facing feature must include Simplified Chinese (`zh_CN`), English (`en_US`) and Japanese (`ja_JP`) text in the same change. This applies to menus, dialogs, tooltips, viewport overlays, validation messages and status/monitor labels.
- For every user-visible software update, maintain matching dated entries in `CHANGELOG.md`, `CHANGELOG.zh-CN.md` and `CHANGELOG.ja.md` in the same change before publishing it. Cover features, fixes, changed defaults/parameters, compatibility and delivery behavior; group internal-only maintenance without burying the user impact in commit messages. Preserve previous entries and the three README changelog links. Bind historical summaries to source commits, and distinguish implemented changes, verified acceptance, public releases and local installation; pending or inconclusive checks remain explicit. This requirement applies to the original Codex project chat and every existing or future fork; forks read the current shared project rules before resuming work and preserve concurrent edits.
- Use the native translation catalog and its validation command; never introduce unlocalized UI literals. Preserve placeholders, keyboard shortcuts, numeric units and machine-facing identifiers. Do not translate user filenames, project data, JSON keys, CLI flags or external raw logs.
- Language selection applies immediately. Bind persistent UI text through `AppLanguage` and refresh dynamic labels on language changes without rebuilding model/worker state; do not add restart-only language behavior.
- Use consistent photogrammetry, point-cloud, mesh and 3D transformation terminology. Consult `docs/LOCALIZATION.md` and its glossary; reference official CloudCompare, Metashape and Blender terminology when adding terms.
- Validate translations and package files without opening local windows, then commit and push authorized changes to `main` to run the relevant remote native tests. Retain remote logs/screenshots and report incomplete or pending acceptance explicitly. Deliver the verified desktop package and preserve existing projects, settings, and running user sessions.
- For software-upgrade delivery requests, include updating the user's local installation after the applicable verification and authorization; a push, CI success, extracted files or installer link alone is not an installed update. Read back the active pointer, executable digest and recognized native entry points. Do not infer permission to bypass trust/acceptance gates, restart or foreground applications, migrate bootstrap protocols or perform a new exceptionally long phase. Documentation-only or review requests do not themselves authorize installation changes.
- For portable desktop updates, read `docs/NATIVE_UPDATES.md` and publish verified releases through the managed-installation publisher. Keep desktop, Start menu and taskbar entry points on the stable native launcher. Delivery is complete when `current.json`, the active executable digest and every recognized native shortcut agree; preserve running and rollback versions. The fixed-directory setup installer is a separate adapter.
